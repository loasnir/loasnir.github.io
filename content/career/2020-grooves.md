株式会社Grooves（2020-11 〜 2024-09）

## 役割

エンジニアリングマネージャー

エンジニアとして入社し、半年後に開発チームマネージャーを拝命し EM となる。スクラムマスターも兼任し、メンバー増員に伴い複数のスクラムチームを立ち上げ。

「1人でも多くの人がバリューを発揮できる組織を作る」というミッションを実践できる環境であること、メンバーの裁量が大きくそれを支えるカルチャーがあることを理由に入社を決めた。

## 任されたこと

1. **開発チーム メンバー期**: 再編されたチームでプレイングマネージャー的に動き、ライブラリ更新の遅滞や要望の積み残しに対応。開発者だけでは手が足りず、外部ベンダーと組んでプロジェクトを推進しながら自らも開発に加わった。
2. **開発チーム マネージャー期（単一チーム）**: 空席となったチームのマネージャーを引き受け、EM 経験ゼロから守破離の守で学習。増員（正社員採用／業務委託）を進めながら開発チームを立ち上げ、認証・認可基盤リプレース等のベンダー協業プロジェクトのマネジメント・ベンダーコントロールを担った。
3. **開発チーム マネージャー期（複数チーム）**: 3つの実働チームに対して1つの統括チームという編成。職能横断（PdM／デザイナー／エンジニア）のスクラムチームを構築し、開発速度を向上。スクラムマスターを兼任し、各チームマネージャーとの協働で組織・業務フローの設計を主導した。

## 判断したこと

1. **EM 経験ゼロで引き受け、まず「守破離の守」を選んだ**
   前任 EM が別チームへ異動したことで空席となったマネージャーを引き受けたが、EM としての経験はほぼ無い状態だった。初期から大胆な施策を打つのではなく、前任の型をそのまま学習することを優先し、独自色を出すのはその後にした。判断の速さより、土台を壊さないことを優先した選択。

2. **複数チーム化にあたり、実働チームと統括チームを分け、職能横断で組んだ**
   同一プロダクトに複数のスクラムチームを走らせるノウハウが社内になく、手探りで編成を決める場面だった。3つの実働チームに対して1つの統括チームを置く形にし、さらに PdM／デザイナー／エンジニアを分業させず1つのスクラムチームに内包する判断をした。縦割りのままチームを増やすと職能間の情報格差と手戻りが拡大すると見て、先に構造を変える方を選んだ。

3. **ベンダー協業の認証基盤リプレースで、委託にとどめず自らも開発に入った**
   認証・認可基盤を Auth0 に置き換えるプロジェクトで、当初は計画・設計を担い開発をベンダーに委ねる分担だったが、Auth0 の知見がチーム全体に無い状態だと気づき、自分もエンジニアとして開発に加わる判断に切り替えた。役割分担の効率よりも、チーム全体の知識が偏らないことを優先した。

4. **認可基盤リプレースは、要件がスコープ内で収まらないと判明した時点で中止した**
   認証基盤に続けて進めていた認可基盤リプレースで、進行中に要件のスコープが拡大し、導入予定だった仕組みでは満たせないことが判明した。設計をやり直して続行するのではなく、その時点でプロジェクトを中止する判断をした。

## 残したもの

- 実働チーム＋統括チームという、複数スクラムチームを運用するための編成の型
- PdM／デザイナー／エンジニアを内包した職能横断スクラムチームの運営文化
- 正社員採用と業務委託を組み合わせた増員・チーム立ち上げの進め方
- ベンダーと協業しながらプロジェクトを推進するマネジメント・コントロールの実務知見
- スクラムマスター兼任による開発フローの定着

## 使った技術

- サーバーサイド: Ruby / Ruby on Rails
- フロントエンド: React / TypeScript
- インフラ: MySQL / Docker / AWS
- 運用監視: Datadog / Sentry
- CI/CD: CircleCI
